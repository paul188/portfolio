## Abstract

<div className="paper-abstract">
<p>BIDS-Eye answers questions such as <em>"EEG data of people with Alzheimer's disease and of healthy people in the same dataset"</em> over <a href="https://openneuro.org">OpenNeuro</a>, the main public repository for brain-imaging research data. It indexes the metadata of 1,721 datasets (2.7 million files, 75,724 participants, 1,509 linked papers) into PostgreSQL and translates each question into SQL.</p>
<p>The first version let one language model write the whole query. The current version restricts the model to reading the question into a typed plan. Deterministic code resolves the terms, builds and repairs the SQL, and decides what to do when a dataset does not record the field a filter asks about. Every change is scored against judged answers. On 56 held-out questions, grading missing fields as evidence raised recall from 35% to 50% and lowered precision from 74% to 63%. On 65 real requests collected from forums and papers, the deployed search returns 50% of the correct datasets and the development branch 61%. A plain BM25 ranking still beats the pipeline on one benchmark, and Section 5 explains why.</p>
<p>Live at <a href="https://www.bidseye.xyz">bidseye.xyz</a>: GitHub sign-in, 20 searches a day per account.</p>
</div>

## 1. Problem

Every OpenNeuro dataset follows BIDS, the Brain Imaging Data Structure, a community standard for file names and metadata files. The layout is uniform and the content is uneven. A researcher's question usually combines criteria whose answers live in different places.

  <caption><strong>Table 1.</strong> Three criteria from real requests and where a dataset answers them.</caption>
  <thead><tr><th>Criterion</th><th>Where the answer lives</th></tr></thead>
  <tbody>
    <tr><td>"task fMRI with a repetition time below 1 second"</td><td>a scanner setting in a JSON file next to each scan</td></tr>

    <tr><td>"videos of people talking"</td><td>a free-text README, or only the paper</td></tr>
  </tbody>
</table>

Read formally, a question is a conjunction of conditions, and the answer is the set of datasets that satisfy all of them:

<BlockMath math="A(q) \;=\; \{\, d \;:\; c_1(d) \wedge c_2(d) \wedge \dots \wedge c_k(d) \,\}" />

The difficulty is that <InlineMath math="c_i(d)" /> is often unknown. Only 231 of the 1,721 datasets record a coded diagnosis, and about half record no participant ages. SQL treats an unknown comparison as false, so a strict query drops every dataset that is silent on one field. Section 3 replaces that behaviour.

## 2. Pipeline

**Indexing.** A crawler lists each dataset in OpenNeuro's public S3 bucket, downloads the small metadata files and creates every scan as an empty 0-byte file, which is enough for the reference BIDS parser to read the tree. A language model then reads each README once and extracts which conditions the study covers and in what role (patients, controls, excluded, mentioned). Every extracted claim carries a quote, and code verifies that the quote occurs in its source. This lets a diagnosis filter find "patients with bipolar disorder" without matching "bipolar electrodes".

**Design rule.** At query time the model decides structure and code decides values. The single-prompt version failed mostly through the model's free choices. It turned the asker's wish words into required text (`standard & manner`), searched README text for a fact the catalogue stores in a column, and once joined 75,724 participants against 2.7 million files. Each stage in Figure 1 removes one of those freedoms.

**Stage 1: intent parsing.** The model returns a typed plan, a Pydantic object. It names participant groups, scan requirements, filters and free-text topics, and it never picks a database value. The plan keeps distinctions that a keyword list loses. "Patients and controls" is two groups that must both be present. "Bipolar disorder, schizophrenia or ADHD" is one group in which any diagnosis suffices.

**Stage 2: vocabulary resolution.** Each term is linked to the codes the database stores, through a cascade: exact match on labels and synonyms, fuzzy match (RapidFuzz WRatio ≥ 80), then biomedical embeddings (BioLORD-2023-C at cosine ≥ 0.75, SapBERT at ≥ 0.65). A term without a match is searched as text, and the plan records the miss. The vocabulary holds 1,459 concepts with 25,298 synonyms and can be browsed as an [interactive graph](/bids-eye-knowledge-graph.html). The benchmarks changed two decisions here. An ambiguous term now resolves to all of its readings, because picking one by synonym weight cost recall. Institution names are matched on normalised word tokens, because an embedding places "University of Washington" next to "Washington University".

**Stage 3: SQL construction.** When a plan consists of participant groups and plain scan requirements, a compiler† writes the SQL and no second model call happens. The compiler is a whitelist: every plan field it does not know must be empty, otherwise the question goes to the model. It handles 18 of the 70 real requests with identical results, and generation takes 2.4 to 4 seconds, down from 4 to 21. All other questions go to the model with the resolved codes, a schema built at startup from what the database actually contains, and worked examples chosen by similarity from a pool of 319. The model never writes a text predicate. It copies a placeholder such as `text_match('epilepsy | epileptic | seizure', 'short')`, and code expands it.

**Stage 4: rewriting.** A rewriter parses the SQL with sqlglot and applies fixed rules. The most consequential rule is the text fallback. Because so few datasets carry a diagnosis code, every coded filter becomes "the code, or these words in the dataset's short fields", which is the `OR text_match(…)` branch in Figure 1.

**Stage 6: query guard†.** On 14 November 2026 a generated query joined every participant with every file of each dataset, and the sort filled the server's disk. Each query now passes four independent checks: a static analysis of the parsed SQL (one plain SELECT, every join conditioned, participants and files never joined at the same level), an `EXPLAIN` row estimate, per-transaction limits on time and memory, and a concurrency cap. When the database or the guard rejects a query, the model receives the error once and the response is flagged as self-corrected.

All model calls go through one client that walks a cascade (Gemini 2.5 Flash, Pro, Flash-Lite, then Claude) inside a time budget per question. If no model answers, the search degrades to a keyword search.

## 3. Evidence tiers

A failure analysis on the first benchmark showed that most missed datasets failed a filter on a field they do not record. A strict `age <= 12` drops a dataset titled "MRI data of 3–12 year old children" that lists no ages.

Stage 5 therefore grades each condition on each dataset with one of four states:

<BlockMath math="s_i(d) \in \{\, \text{confirmed},\ \text{probable},\ \text{possible},\ \text{contradicted} \,\}" />

A condition is *confirmed* when it holds on recorded data. It is *probable* when a weaker form holds: some of the search words match, the words occur only in a paper the dataset names, or the README names the asked group. It is *possible* when the field is missing and nothing hints either way, and *contradicted* when the recorded value does not fit. The search returns a dataset when every condition is at least probable and at most one falls short of confirmed:

<BlockMath math="d \in R(q) \iff \forall i:\ s_i(d) \in \{\text{confirmed}, \text{probable}\} \;\;\wedge\;\; \bigl|\{\, i : s_i(d) = \text{probable} \,\}\bigr| \le 1" />

  <ClickableImage src="/images/projects/bids-eye-tiers.png" alt="Evidence tiers on an example question: five datasets, the state of each condition, and whether the dataset is returned" />
  <p className="paper-caption"><strong>Figure 2.</strong> Evidence tiers on one question (schematic datasets). A strict filter returns only the first row. The tiers also return the second and label it.</p>

Results are ordered by their weakest state, then by text rank. Second-tier results appear under their own heading, each with its reason ("ages not recorded; the description names the age group"). Facts read from the files themselves, such as scan type and subject counts, stay hard filters. Keeping *possible* datasets was measured and rejected: it added 2,211 result rows for 0.4 points of recall.

## 4. Evaluation

The prototype's regression test checked 77 queries for SQL fragments, which showed that a query ran and left open whether the right datasets came back. Three benchmarks with judged answers replaced it.

<table className="paper-table">
  <caption><strong>Table 2.</strong> Benchmarks. A question–dataset pair is one judgement of whether a dataset answers a question.</caption>
  <thead><tr><th>Benchmark</th><th>Questions</th><th>Ground truth</th></tr></thead>
  <tbody>
    <tr><td>Written questions</td><td>227, of which 60 held out</td><td>pooled candidates, graded by a model judge against a written criterion</td></tr>
    <tr><td>Real requests</td><td>70 from forums, GitHub issues and the methods sections of papers</td><td>13,795 pairs: 9,763 decided by recorded facts, 3,739 by a judge, 293 by stated presumption or review</td></tr>
    <tr><td>Reuse papers</td><td>1,170 from 561 papers that reused a dataset</td><td>the dataset the authors used, so no judge is needed</td></tr>
  </tbody>
</table>

Four choices keep the numbers trustworthy.

- **Pooling.** Judging 1,721 datasets per question is infeasible. As in information-retrieval evaluations, every dataset that any generous signal points at (keywords, codes, ages, the 20 nearest by embedding) becomes a candidate, and only candidates are judged. A direct check of the assumption: of 37 datasets in the live top 20 that had not been candidates, 1 was relevant and 4 were partially relevant.
- **Audited judges.** The judges are language models. A blind second judge re-read 383 "not relevant" labels and called 5 of them relevant (1.3%). Two independent reviewers re-labelled 150 items blind and agreed with the judge on relevant versus not in 94%. On the real requests, recorded facts and the judge disagreed in 7 cases, and the judge was right in all 7.
- **Held-out discipline.** Writers who saw neither search code nor results wrote the 60 held-out questions after the others. I read held-out scores as averages only, once per finished change, and add no vocabulary, example or prompt text because of a held-out question.
- **Record and replay.** A recorded run stores each question's plan, resolved codes and raw model SQL. A replay answers both model stages from that file, so a change to any deterministic stage is scored on all 70 requests without a model call, in 16 minutes instead of 34. Replayed results matched the original on 69 of 70 requests.

## 5. Results

(a) Four successive versions on the development questions. (b) One translation scored with the tiers off and on. (c) The 65 real requests that have an answer in the catalogue. On the development questions, recall rose from 32% to 59% in two days while precision fell from 68% to 59%. The held-out pair in panel (b) isolates the tiers and is the number to quote: 15 points of recall for 11 points of precision, with the lower-confidence results ranked last and labelled. On the real requests the development branch reaches 61% recall at about the same precision, and the requests with no correct result drop from 14–16 to 7–9. Repeated runs differ by one or two points. All 70 real requests have since served to find defects, so they are a development set and their scores overstate performance on unseen requests.

**Where the search failed.** For the deployed run, I traced each failing request to the SQL condition that caused it. One read-only query per request evaluated every top-level condition on every dataset (186 conditions), which gives the number of correct answers each condition excludes on its own.

For "data organised in a standard manner", the condition `standard & manner` let 11 of 986 correct datasets through. Without it the search finds all 986. This table set the work that followed: the plan compiler, the handling of "or" lists, and a registry that fixes for each kind of filter which evidence decides it.

**A baseline that still wins.** On a development subset of 292 reuse-paper questions, the deployed pipeline put the dataset the authors had used on the first page for 23% and returned nothing for 48%. A BM25 keyword ranking over name, study fields and README, with no language model, reaches 68% on the 830 development questions. The two question sets differ, yet the direction is clear. A long sentence of need turns into many strict filters, and one wrong filter empties the result, while BM25 always returns its best guess. The pipeline is therefore moving toward fewer hard conditions and more ranked evidence.

## 6. Limits

- The deployed search misses half of the correct answers to real requests, and about 40% of what it returns is not a correct answer.
- Language models judged both benchmarks. The audits bound the error, and a person has not read every label.
- The gold set covers 70 requests, all in English, and now serves as a development set. An unbiased number needs new requests.
- The pipeline has not yet run on the 340 held-out reuse-paper questions.
- 278 public OpenNeuro datasets are missing from the catalogue.
