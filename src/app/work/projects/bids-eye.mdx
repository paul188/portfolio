BIDS-Eye is a natural-language search engine over **OpenNeuro**, the primary open-access repository for human neuroimaging data (MRI, fMRI, EEG, MEG, PET). It answers queries like *"datasets with ≥ 50 left-handed participants who did an n-back task with fMRI"* by crawling ~1,000 datasets from AWS S3, indexing them into a unified PostgreSQL database, and translating free-text queries into SQL through a three-tier RAG pipeline backed by a 1,466-concept biomedical ontology.

## 1. Data Source: OpenNeuro and BIDS

OpenNeuro hosts thousands of neuroimaging datasets on AWS S3, most of them publicly accessible. Every dataset follows the Brain Imaging Data Structure (BIDS), a community standard for how a dataset is organised on disk. File paths and JSON sidecars carry the metadata:

```
ds000228/
├── dataset_description.json      ← name, authors, license, BIDS version
├── participants.tsv               ← one row per subject: age, sex, handedness, diagnosis
├── sub-001/
│   ├── anat/
│   │   └── sub-001_T1w.nii.gz
│   └── func/
│       ├── sub-001_task-rest_bold.nii.gz
│       └── sub-001_task-rest_bold.json   ← sidecar: TR, slice timing, etc.
└── derivatives/
    └── fmriprep/sub-001/...
```

Because every dataset follows the same conventions, one SQL database can cover thousands of datasets without bespoke parsing.

---

## 2. Database Schema

pybids (the reference Python BIDS library) builds an in-process SQLite index of one dataset at a time. BIDS-Eye generalises this to a persistent PostgreSQL database spanning thousands of datasets.

1. **Hot entities get real columns.** The most commonly filtered properties (`subject`, `session`, `task`, `suffix`, `datatype`, `sex`, `handedness`, `diagnosis`) are indexed columns.
2. **Cold entities go into JSONB overflow.** ~30 secondary BIDS entities and arbitrary sidecar metadata land in `other_entities` (JSONB with GIN index), queryable without schema migrations.
3. **Upserts are idempotent.** Every write uses `ON CONFLICT … DO UPDATE`, so re-crawling a dataset refreshes rows and never duplicates them.

Four tables hold the data: `bids_datasets` (one row per dataset, raw or derivative), `bids_objects` (one row per file), `bids_participants` (one row per subject per dataset) and `object_associations` (directed edges between files, such as an image and its JSON sidecar).

---

## 3. Crawlers

Cloning all raw imaging files (`.nii.gz`) would require terabytes. BIDS-Eye uses **ghost indexing**:

1. An anonymous boto3 client lists the `openneuro.org` S3 bucket.
2. Metadata files (`.json`, `.tsv`) are downloaded in full. JSON files are repaired for common authoring mistakes such as trailing commas.
3. Imaging files are created as empty stubs. 0 bytes is enough for pybids to see them in the tree.
4. pybids indexes the local mirror, and BIDS-Eye upserts that index into PostgreSQL with all objects marked `is_remote=True`.

Some datasets are access-restricted on S3. A fallback crawler queries the OpenNeuro GraphQL API and synthesises participant and object rows, marked as synthetic through `source_type`. APScheduler runs a crawl cycle on a configurable interval (default: 1 hour), one dataset at a time.

## 4. Vocabulary Normalisation

Raw BIDS datasets are terminologically inconsistent. The same diagnosis appears as `"MDD"`, `"major depressive disorder"`, `"clinical depression"`, `"depression"`, and `"296.20"` across different datasets. Without normalisation, no cross-dataset query is possible.

`value_mappings.yaml` is the unified ontology that maps all surface forms onto canonical codes: **1,466 concepts across 8 categories**.


```yaml
diagnosis:
  major_depressive_disorder:
    label: "major depressive disorder"
    standard_code: "major_depressive_disorder"
    broader: [mood_disorders]
    synonyms:
      - term: "MDD"
        weight: 0.85
      - term: "296.20"        # ICD-9 code as synonym
        weight: 0.6
    codes: [mdd, depression, depressive_disorder]
```

A concept can have multiple parents via `broader`. Each synonym carries a weight:

The retriever raises the fuzzy-match threshold for low-confidence synonyms:

```python
effective_threshold = 80 + (1.0 - weight) × 8
```

`"autism"` (weight 1.0) matches at score ≥ 80. `"developmental disorder"` (weight 0.3) requires score ≥ 85.6, so it only matches if the user typed it nearly verbatim.

### Synonym Generation and Collisions

Synonyms are mined from three corpus sources and validated by an LLM: dataset descriptions in PostgreSQL, the CrossRef REST API, and the OpenAlex REST API.

A collision is a synonym in concept A that is also the label or a high-weight (≥ 0.7) synonym of concept B. Detection uses RapidFuzz WRatio. The `task` field alone had **239 CRITICAL** and **1,075 HIGH** collisions, most commonly a parent concept claiming a child's label. A fix script applies 299 curated removals.

## 5. Natural-Language Query to SQL

Gemini handles high-level reasoning. A domain-specific RAG layer (`value_mappings.yaml` plus biomedical embeddings) resolves vocabulary. SQLCoder (fine-tuned Code Llama) was evaluated and abandoned: it requires a GPU inference endpoint and has no neuroscience vocabulary.

Example query:

> *"datasets with resting-state fMRI and at least 20 autistic participants"*

### Stage 1: Entity Extraction

Gemini 2.5 Flash returns a structured Pydantic object with the raw terms per field: `diagnosis=["autism"]`, `task=["resting state"]`, `datatype=["fMRI"]`.

### Stage 2: Resolving Terms to Canonical Codes

This stage resolves a surface form to a canonical database key, like the string `autism_spectrum_disorder` that goes straight into a SQL `WHERE` clause. It is closer to biomedical entity linking than to generative RAG.


```
User term
    │
    ▼
Tier 1 — Exact match       O(1) dict lookup against leaf_db / group_db
    │ miss
    ▼
Tier 2 — Fuzzy (WRatio)    weight-adjusted threshold: 80 + (1.0 − w) × 8
    │ score < threshold
    ▼
Tier 3a — BioLORD-2023-C   cosine ≥ 0.75  (SNOMED-CT / MedDRA)
    │ miss
    ▼
Tier 3b — SapBERT           cosine ≥ 0.65  (UMLS 4M+ entities)
    │ miss
    ▼
VOCAB MISS → ILIKE hint injected into SQL
```

- **Embeddings.** BioLORD has very high precision for clinical terms with narrower coverage, so it runs first at the higher threshold. SapBERT has higher recall and catches the longer tail. Embeddings for all ~29 000 synonym surface forms are pre-computed, so only the user's term is embedded at query time.
- **Multi-field search.** `"fMRI"` is both a `datatype` (`func/` folder) and a `suffix` (`bold`). The resolver searches `datatype`, `suffix`, and `task` in parallel and returns all hits.
- **Hierarchy pruning.** If a result set contains both a concept and one of its ancestors, the ancestor is dropped. Otherwise the query would match far more data than the user intended.
- **Vocabulary misses.** When all tiers fail and the LLM generates a `WHERE` filter with a made-up code, that filter is stripped and a prepared `ILIKE` is injected. The query falls back to approximate text search and avoids SQL errors or empty results.

Resolved output:

```json
{
  "diagnosis": ["autism_spectrum_disorder"],
  "task":      ["resting_state"],
  "datatype":  ["func"],
  "suffix":    ["bold"]
}
```

### Stage 3: SQL Generation

Resolved codes, the full schema DDL, and few-shot examples are assembled into a Gemini prompt.

```sql
SELECT DISTINCT d.id, d.name, d.accession_id,
       COUNT(DISTINCT p.participant_id) AS n_participants
FROM bids_datasets d
JOIN bids_participants p ON p.dataset_id = d.id
JOIN bids_objects o ON o.dataset_id = d.id
WHERE p.diagnosis = 'autism_spectrum_disorder'
  AND o.task = 'resting_state'
  AND (o.datatype = 'func' OR o.suffix = 'bold')
GROUP BY d.id, d.name, d.accession_id
HAVING COUNT(DISTINCT p.participant_id) >= 20
ORDER BY n_participants DESC;
```

### Stage 4: Execution and Error Correction

If the SQL fails, the session is rolled back and Gemini receives the original question, the failed SQL, the schema DDL, and the PostgreSQL error message. The corrected SQL is executed once and the response is flagged `self_corrected: True`. If the correction also fails, the original error is returned.

**Regression testing:** 77 hand-crafted queries run after any pipeline change. They check minimum result count, required SQL fragments, and forbidden patterns (e.g. ILIKE on a canonical-code column).
